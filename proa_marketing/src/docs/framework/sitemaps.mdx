Register discovery endpoints on `FrameworkBuilder`. Its public origin and runtime [base path](/docs/framework/deployment) determine the URLs in both documents. Read environment variables once at startup; handlers do not need to repeat that configuration.

## Run an application

Configure discovery endpoints and start the HTTP server in `src/main.rs`. Route definitions are abbreviated below; replace the comment in `vec![]` with your application routes. The example loads the app's generated manifest from `dist/island-manifest.json`.

```rust filename="src/main.rs"
use std::time::Duration;

use proa_framework_axum::{
    BasePath, FrameworkBuilder, IslandManifest, RobotsTxt, SitemapUrl,
    router_from_spec, serve,
};

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let manifest = IslandManifest::load_from_path("dist/island-manifest.json")?;
    let base_path = BasePath::new(&std::env::var("PROA_BASE_PATH").unwrap_or_default())?;
    let origin = std::env::var("PUBLIC_BASE_URL")?;

    let (routes, metadata) = router_from_spec(vec![/* your application routes */]);

    let app = FrameworkBuilder::new(manifest)
        .with_dynamic_routes_and_metadata(routes, metadata)
        .with_base_path(base_path)
        .with_public_origin(&origin)?
        .with_sitemap([
            SitemapUrl::new("/")?,
            SitemapUrl::new("/pricing")?.lastmod("2026-10-25")?,
        ])
        .with_robots(RobotsTxt::new().allow("/")?.disallow("/admin")?)
        .try_build()?;

    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000").await?;
    serve(listener, app, Duration::from_secs(30)).await?;
    Ok(())
}
```

From the application crate, run with an empty base path for local development:

```bash
PUBLIC_BASE_URL=http://127.0.0.1:3000 PROA_BASE_PATH="" cargo run
```

Visit `http://127.0.0.1:3000/sitemap.xml` for the sitemap and `/robots.txt` for crawler rules. The example sitemap lists `/` and `/pricing`; register those page routes in the application route list.

`try_build()` returns an Axum router. Pass it to `serve()` with a bound TCP listener to start accepting requests. The server runs until Ctrl+C or SIGTERM, then allows up to 30 seconds for in-flight requests to finish.

## Configure public URLs

The public origin contains only a scheme, host and optional port: `https://example.com`, without the app prefix. With `PROA_BASE_PATH=/apps/demo`, the generated sitemap contains `https://example.com/apps/demo/pricing`. Robots rules become `Allow: /apps/demo/` and `Disallow: /apps/demo/admin`. When both endpoints are enabled, robots.txt automatically advertises `https://example.com/apps/demo/sitemap.xml`.

Configuration order does not matter. The documents use the final `with_base_path` and `with_public_origin` values when the router is built. Origins are explicit configuration; request `Host` and forwarded headers do not override them.

The endpoints are individually opt-in. `with_sitemap` installs `/sitemap.xml`; `with_robots` installs `/robots.txt`. Do not register custom handlers at the same paths when using these methods. A robots-only document needs no public origin unless you also enable the sitemap. Existing absolute sitemap links added with `RobotsTxt::sitemap` are preserved; an identical automatic sitemap link is not duplicated.

## Sitemap entries

Entries are application-local paths or absolute `http`/`https` URLs on the configured origin. Local paths get the builder's base path exactly once. Absolute entries retain their spelling and are not prefixed.

Sitemap entries are explicit: registering a page with `Route::page` does not automatically add it to the sitemap. Include the public pages you want crawlers to discover in `with_sitemap`.

Each entry can also carry optional metadata:

```rust
use proa_framework_axum::{ChangeFreq, SitemapPriority, SitemapUrl};

let pricing = SitemapUrl::new("/pricing")?
    .lastmod("2026-10-25")?
    .changefreq(ChangeFreq::Weekly)
    .priority(SitemapPriority::tenths(8).expect("priority within 0..=10"));
```

Origins compare scheme, host and effective port. An omitted port matches `:443` for HTTPS or `:80` for HTTP. Scheme and host matching is ASCII case-insensitive, and equivalent IPv6 spellings match. Different hosts, schemes or effective ports are rejected.

Query strings are XML-escaped. Paths and URLs reject ASCII controls and XML-forbidden characters. `lastmod` is a real `YYYY-MM-DD` calendar date, including leap years. Priority is stored in tenths from `0.0` to `1.0`. Each final loc must be shorter than 2048 bytes.

`try_build()` validates and renders these static documents once, then serves their shared bytes on each request. It returns a `DiscoveryError` for a missing public origin, cross-origin entry or invalid composed URL. The existing `build()` API also works, but panics on invalid discovery configuration. Axum's duplicate-route restrictions apply to both.

## Multiple sitemaps

Use `with_sitemaps` when the site needs separate page, product, or blog documents. Each `SitemapFile` contains page entries; its ID determines the document's route.

```rust
use proa_framework_axum::{FrameworkBuilder, RobotsTxt, SitemapFile, SitemapUrl};

let app = FrameworkBuilder::new(manifest)
    .with_dynamic_routes_and_metadata(routes, metadata)
    .with_public_origin("https://example.com")?
    .with_sitemaps([
        SitemapFile::new("pages", [
            SitemapUrl::new("/")?,
            SitemapUrl::new("/pricing")?,
        ])?,
        SitemapFile::new("products-0", [
            SitemapUrl::new("/products/1")?.lastmod("2026-10-25")?,
        ])?,
    ])
    .with_robots(RobotsTxt::new())
    .try_build()?;
```

The builder installs:

| Route | Contents |
|---|---|
| `/sitemap.xml` | A `<sitemapindex>` linking to both documents. |
| `/sitemap/pages.xml` | A `<urlset>` containing `/` and `/pricing`. |
| `/sitemap/products-0.xml` | A `<urlset>` containing `/products/1`. |
| `/robots.txt` | Advertises `/sitemap.xml`, the index. |

The final public origin and base path apply to index links and page URLs. With a mount of `/apps/demo`, the index links to `https://example.com/apps/demo/sitemap/pages.xml`; incoming handler paths remain unprefixed. Forward both the index and its child documents through the proxy.

IDs must be nonempty and contain only ASCII letters, digits, `-`, or `_`. Duplicate IDs and an empty file list return startup errors. `with_sitemap` and `with_sitemaps` select alternative modes; the last call replaces the previous configuration. One file passed to `with_sitemaps` still produces an index and a child document.

### Async generation from application data

Await an application-owned `generate_sitemaps` function before building the router. It can query a database or CMS and return named documents. The example below assumes your application's `Database::published_products()` returns products with `path` and `last_modified` strings.

```rust
use proa_framework_axum::{
    DiscoveryError, FrameworkBuilder, RobotsTxt, SitemapFile, SitemapUrl, MAX_SITEMAP_ENTRIES,
};

async fn generate_sitemaps(db: &Database) -> anyhow::Result<Vec<SitemapFile>> {
    let products = db.published_products().await?;
    let mut files = vec![SitemapFile::new("pages", [
        SitemapUrl::new("/")?,
        SitemapUrl::new("/pricing")?,
    ])?];

    for (id, products) in products.chunks(MAX_SITEMAP_ENTRIES).enumerate() {
        let urls = products.iter().map(|product| {
            SitemapUrl::new(product.path.as_str())?
                .lastmod(product.last_modified.as_str())
        }).collect::<Result<Vec<_>, DiscoveryError>>()?;
        files.push(SitemapFile::new(format!("products-{id}"), urls)?);
    }
    Ok(files)
}

// Inside async main, before binding the listener:
let app = FrameworkBuilder::new(manifest)
    .with_dynamic_routes_and_metadata(routes, metadata)
    .with_base_path(base_path)
    .with_public_origin(&origin)?
    .with_sitemaps(generate_sitemaps(&db).await?)
    .with_robots(RobotsTxt::new())
    .try_build()?;
```

This uses the same named-document idea as [Next.js generateSitemaps](https://nextjs.org/docs/app/api-reference/functions/generate-sitemaps). Proa's generator returns each document's entries together with its ID. It is ordinary application code, so it can borrow database handles and return application-specific errors without framework callback or lifetime constraints.

Generation runs **once at application startup**, followed by validation and XML rendering. HTTP requests serve cached bytes and do not rerun the generator. New content requires regenerating/restarting the app; for request-time generation or application-managed refresh, use custom handlers with `sitemap_xml` and `sitemap_index_xml`.

Both sitemaps and indexes enforce the [protocol limits](https://www.sitemaps.org/protocol.html#index): at most 50,000 entries and 50 MiB of uncompressed UTF-8 XML per document. The byte check includes XML escaping. Splitting by entry count alone may still exceed the byte limit for long URLs; use smaller batches in that case. An oversized document returns a `DiscoveryError` rather than silently serving invalid XML. Dates should reflect actual content changes, rather than the time the generator runs.

## Generate robots.txt

Use the same async generation pattern as sitemaps:

```rust
.with_robots(generate_robots(&db).await?)
```

`generate_robots` is application-owned code returning `Result<RobotsTxt, YourError>`. It can read configuration, a database, or a CMS before the router is built. For example, assuming your application's `Database::crawler_exclusions()` returns a list of application-local path strings:

```rust
use proa_framework_axum::RobotsTxt;

async fn generate_robots(db: &Database) -> anyhow::Result<RobotsTxt> {
    let paths = db.crawler_exclusions().await?;
    let mut robots = RobotsTxt::new().group("*")?;
    for path in paths {
        robots = robots.disallow(&path)?;
    }
    Ok(robots)
}
```

Pass the result to the same builder that configures the sitemap:

```rust
let app = FrameworkBuilder::new(manifest)
    .with_dynamic_routes_and_metadata(routes, metadata)
    .with_base_path(base_path)
    .with_public_origin(&origin)?
    .with_sitemaps(generate_sitemaps(&db).await?)
    .with_robots(generate_robots(&db).await?)
    .try_build()?;
```

Generation and text rendering happen **once at startup**, and requests serve cached bytes. The final builder base path applies to allow/disallow paths exactly once. Existing explicit sitemap links are preserved, and the generated sitemap or index is advertised automatically without an identical duplicate. Use a custom handler with `robots_txt` for request-time generation or application-managed refresh.

### Bot-specific rules and optional directives

As in [Next.js robots metadata](https://nextjs.org/docs/app/api-reference/file-conventions/metadata/robots), configure different groups for different bots, several sitemap links, and optional directives:

```rust
use std::time::Duration;
use proa_framework_axum::RobotsTxt;

let robots = RobotsTxt::new()
    .group_agents(["Applebot", "Bingbot"])?
    .allow("/")?
    .disallow("/private/")?
    .crawl_delay(Duration::from_millis(1500))
    .directive("Clean-param", "ref /articles/")?
    .group("*")?
    .allow("/")?
    .disallow("/private/")?
    .host("https://example.com")?
    .sitemap("https://example.com/news-sitemap.xml")?;
```

`group_agents` emits consecutive `User-agent` lines sharing one rule group. `group` starts a new group; subsequent allow/disallow rules, crawl delay, and custom directives apply to that group. Calling a rule or per-group option before starting a group creates a wildcard group. Repeating `directive` emits repeated fields, preserving their names and values. Specific matching groups have their own rules; the wildcard group is a fallback, rather than a set of rules automatically inherited by named bots.

`crawl_delay` uses a Rust `Duration` and renders exact decimal seconds, so 1500 milliseconds becomes `Crawl-delay: 1.5`. `host` accepts a hostname with optional port, or an HTTP(S) origin; it is explicit document configuration. It is not inferred from request headers or automatically set by the public origin.

`Host`, `Crawl-delay`, and custom fields are optional crawler extensions. Support depends on the crawler; for example, [Google ignores crawl-delay](https://developers.google.com/crawling/docs/robots-txt/robots-txt-spec). Custom directive names must start with an ASCII letter and contain only ASCII letters, digits, or `-`. Values can contain spaces but cannot contain `#` or control characters. Reserved names (`User-agent`, `Allow`, `Disallow`, `Host`, `Sitemap`, `Crawl-delay`) use the typed methods. Extension values render verbatim and do not receive the application's base path.

There is still **one robots.txt document per origin**, containing all user-agent groups and sitemap links. Multiple sitemap documents do not create multiple robots files.

## Origin-root robots.txt

Crawlers fetch `https://example.com/robots.txt`, even when the app lives at `/apps/demo/`. They do not discover robots rules from `/apps/demo/robots.txt`.

Incoming Proa routes stay unprefixed. For a [prefix-stripping proxy](/docs/framework/deployment#serving-behind-a-url-path-prefix), forward origin-root `/robots.txt` to the builder's `/robots.txt` handler in addition to stripping `/apps/demo` for the app's other routes. Builder configuration cannot change the proxy's public routing.

Root-relative robots rules supplied to `with_robots` are application-local paths: pass `/admin`, not `/apps/demo/admin`. The builder's base path replaces any base path already set on the document, so rules are never prefixed twice. A root rule (`/` or `/$`) also renders an end-anchored rule for the bare mount URL, so `disallow("/")` blocks both `/apps/demo` and everything under `/apps/demo/`. Empty rules and wildcard-leading patterns such as `*.pdf$` remain unchanged; those patterns match public paths directly. To scope a wildcard to the mount, use a root-relative rule such as `/*.pdf$`.

Whitespace, `#` and control characters are rejected in user-agent and rule fields. A group with no rules renders an empty `Disallow:` so it does not merge into the next group.

## Custom and dynamic handlers

The standalone `Sitemap`, `SitemapIndex`, `RobotsTxt`, `sitemap_xml`, `sitemap_index_xml` and `robots_txt` APIs remain available for applications that generate documents dynamically or use custom routing. In that mode, pass the application's configured origin and base path explicitly. Standalone robots rules are application paths too; call `RobotsTxt::with_base_path` to render them under the mount prefix. The response helpers use `application/xml` and `text/plain`, both with UTF-8.

If a dynamically generated sitemap or index fails to render, its response helper logs the cause and returns a generic 500. Builder-managed documents are validated at startup instead.
