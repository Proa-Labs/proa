Configure `/robots.txt` on `FrameworkBuilder` to publish crawler rules. The builder applies the final runtime [base path](/docs/framework/deployment) to application-local allow/disallow rules and advertises the generated [sitemap or sitemap index](/docs/framework/sitemaps) when enabled.

## Configure the builder

```rust {6}
use proa_framework_axum::{FrameworkBuilder, RobotsTxt};

let app = FrameworkBuilder::new(manifest)
    .with_dynamic_routes_and_metadata(routes, metadata)
    .with_base_path(base_path)
    .with_robots(RobotsTxt::new().allow("/")?.disallow("/private/")?)
    .try_build()?;
```

`with_robots` is opt-in and installs the `/robots.txt` handler. Do not register a custom handler at the same path when using it. Robots-only configuration needs no public origin; enabling a sitemap on the builder requires `with_public_origin`. For listener binding and `serve()`, see the [complete application example](/docs/framework/sitemaps#run-an-application).

## Async generation

Use the same async generation pattern as [sitemaps](/docs/framework/sitemaps#async-generation-from-application-data):

```rust
.with_robots(generate_robots(&db).await?)
```

`generate_robots` is application-owned code returning `Result<RobotsTxt, YourError>`. It can read configuration, a database, or a CMS before the router is built. For example, assuming your application's `Database::crawler_exclusions()` returns a list of application-local path strings:

```rust {4,7}
use proa_framework_axum::RobotsTxt;

async fn generate_robots(db: &Database) -> anyhow::Result<RobotsTxt> {
    let paths = db.crawler_exclusions().await?;
    let mut robots = RobotsTxt::new().group("*")?;
    for path in paths {
        robots = robots.disallow(&path)?;
    }
    Ok(robots)
}
```

Pass the result to the same builder that configures the sitemap:

```rust {6}
let app = FrameworkBuilder::new(manifest)
    .with_dynamic_routes_and_metadata(routes, metadata)
    .with_base_path(base_path)
    .with_public_origin(&origin)?
    .with_sitemaps(generate_sitemaps(&db).await?)
    .with_robots(generate_robots(&db).await?)
    .try_build()?;
```

Generation and text rendering happen **once at startup**, and requests serve cached bytes. The final builder base path applies to allow/disallow paths exactly once. Existing explicit sitemap links are preserved, and the generated sitemap or index is advertised automatically without an identical duplicate. Use a custom handler with `robots_txt` for request-time generation or application-managed refresh.

## Bot-specific rules and optional directives

As in [Next.js robots metadata](https://nextjs.org/docs/app/api-reference/file-conventions/metadata/robots), configure different groups for different bots, several sitemap links, and optional directives:

```rust {5,8-9,13-14}
use std::time::Duration;
use proa_framework_axum::RobotsTxt;

let robots = RobotsTxt::new()
    .group_agents(["Applebot", "Bingbot"])?
    .allow("/")?
    .disallow("/private/")?
    .crawl_delay(Duration::from_millis(1500))
    .directive("Clean-param", "ref /articles/")?
    .group("*")?
    .allow("/")?
    .disallow("/private/")?
    .host("https://example.com")?
    .sitemap("https://example.com/news-sitemap.xml")?;
```

`group_agents` emits consecutive `User-agent` lines sharing one rule group. `group` starts a new group; subsequent allow/disallow rules, crawl delay, and custom directives apply to that group. Calling a rule or per-group option before starting a group creates a wildcard group. Repeating `directive` emits repeated fields, preserving their names and values. Specific matching groups have their own rules; the wildcard group is a fallback, rather than a set of rules automatically inherited by named bots.

`crawl_delay` uses a Rust `Duration` and renders exact decimal seconds, so 1500 milliseconds becomes `Crawl-delay: 1.5`. `host` accepts a hostname with optional port, or an HTTP(S) origin; it is explicit document configuration. It is not inferred from request headers or automatically set by the public origin.

`Host`, `Crawl-delay`, and custom fields are optional crawler extensions. Support depends on the crawler; for example, [Google ignores crawl-delay](https://developers.google.com/crawling/docs/robots-txt/robots-txt-spec). Custom directive names must start with an ASCII letter and contain only ASCII letters, digits, or `-`. Values can contain spaces but cannot contain `#` or control characters. Reserved names (`User-agent`, `Allow`, `Disallow`, `Host`, `Sitemap`, `Crawl-delay`) use the typed methods. Extension values render verbatim and do not receive the application's base path.

There is still **one robots.txt document per origin**, containing all user-agent groups and sitemap links. Multiple sitemap documents do not create multiple robots files.

## Origin-root robots.txt

Crawlers fetch `https://example.com/robots.txt`, even when the app lives at `/apps/demo/`. They do not discover robots rules from `/apps/demo/robots.txt`.

Incoming Proa routes stay unprefixed. For a [prefix-stripping proxy](/docs/framework/deployment#serving-behind-a-url-path-prefix), forward origin-root `/robots.txt` to the builder's `/robots.txt` handler in addition to stripping `/apps/demo` for the app's other routes. Builder configuration cannot change the proxy's public routing.

Root-relative robots rules supplied to `with_robots` are application-local paths: pass `/admin`, not `/apps/demo/admin`. The builder's base path replaces any base path already set on the document, so rules are never prefixed twice. A root rule (`/` or `/$`) also renders an end-anchored rule for the bare mount URL, so `disallow("/")` blocks both `/apps/demo` and everything under `/apps/demo/`. Empty rules and wildcard-leading patterns such as `*.pdf$` remain unchanged; those patterns match public paths directly. To scope a wildcard to the mount, use a root-relative rule such as `/*.pdf$`.

Whitespace, `#` and control characters are rejected in user-agent and rule fields. A group with no rules renders an empty `Disallow:` so it does not merge into the next group.

## Custom and dynamic handlers

Use standalone `RobotsTxt` and `robots_txt` for request-time generation or application-managed refresh. Pass the application's configured base path to `RobotsTxt::with_base_path` before rendering; allow/disallow rules remain application-local paths. `robots_txt(&robots)` returns a UTF-8 `text/plain` response.

When using a custom handler, configure sitemap links explicitly with `RobotsTxt::sitemap` for an absolute URL or `RobotsTxt::sitemap_path` for an application-local path composed with the origin and base path. Builder-managed documents preserve these links and avoid adding an identical automatic sitemap/index link twice.
