---
title: proa site
description: Validate site structure and print discovered routes.
---

`proa site` commands inspect projects that follow the generated site conventions. Use them after scaffolding, after moving route files, and in CI before deployment.

They work from the nearest parent directory that contains both `Cargo.toml` and `src/`. Pass `--root` when you want to inspect a different project.

```bash
proa site check
proa site routes
```

## Command Summary

| Command | Use it when | Exit behavior |
|---------|-------------|---------------|
| `proa site check` | You want structural diagnostics for the generated site layout. | Exits non-zero when errors are present. |
| `proa site doctor` | You want the same diagnostics using the diagnostic command name. | Same implementation and exit behavior as `site check`. |
| `proa site routes` | You want the route paths implied by `src/pages`. | Exits zero when route discovery succeeds, even when no page files exist. |

## Check

```bash
proa site check
proa site check --root ../my-site
proa site check --json
```

`site check` verifies the expected module structure generated by `proa new site`:

- `src/pages/mod.rs`
- `src/components/mod.rs`
- `src/layouts/mod.rs`
- `src/data/mod.rs`

It also scans Rust page files under `src/pages` and reports an error when a page file does not expose a `handler` or `render` function. `src/islands` is reported as invalid for the generated site convention because islands live in the page or component tree instead of a separate source root.

A passing text run prints:

```text
Proa site check passed for /path/to/site
```

When errors exist, each one prints as an `error:` line and the command exits non-zero.

## JSON Diagnostics

Use `--json` for CI summaries, editor tooling, or scripts:

```bash
proa site check --json > proa-site-check.json
```

The JSON report has a stable shape:

```json
{
  "root": "/path/to/site",
  "errors": [],
  "warnings": []
}
```

Example failures:

```json
{
  "root": "/path/to/site",
  "errors": [
    "missing src/layouts/mod.rs",
    "src/pages/pricing.rs does not expose a handler or render function"
  ],
  "warnings": []
}
```

## Doctor

```bash
proa site doctor
proa site doctor --json
```

`doctor` currently runs the same implementation as `site check`. Use either command for structural diagnostics.

## Routes

```bash
proa site routes
proa site routes --json
```

`site routes` discovers Rust files under `src/pages` and maps them to route paths. Text output is aligned for terminal scanning:

```text
GET  /                                src/pages/home.rs
GET  /docs/getting-started            src/pages/docs/getting_started.rs
GET  /pricing                         src/pages/pricing.rs
```

JSON output returns one object per discovered route:

```json
[
  {
    "method": "GET",
    "path": "/pricing",
    "file": "src/pages/pricing.rs"
  }
]
```

## Route Mapping Rules

Route discovery is convention-based:

| File | Route |
|------|-------|
| `src/pages/home.rs` | `/` |
| `src/pages/index.rs` | `/` |
| `src/pages/pricing.rs` | `/pricing` |
| `src/pages/docs/index.rs` | `/docs` |
| `src/pages/docs/getting_started.rs` | `/docs/getting-started` |

Rules:

- `home.rs` at the top level maps to `/`.
- `index.rs` maps to the containing folder route.
- Underscores become hyphens.
- Nested folders become nested route segments.
- Every discovered route uses `GET`.

This is a page-file convention report. It does not execute the app, inspect Axum router state, or infer dynamic wildcard routes.

## Root Resolution

By default, `site` commands walk upward from the current directory until they find a directory with both `Cargo.toml` and `src/`. Pass `--root` to inspect a different project:

```bash
proa site routes --root /path/to/site
```

Use `--root` in monorepos when your shell is outside the site package:

```bash
proa site check --root apps/marketing
proa site routes --root apps/marketing --json
```

## CI Pattern

For generated Proa sites, add `site check` next to the normal Rust and Proa checks:

```bash
cargo fmt --all --check
cargo check
proa fmt --check --verify src
proa lint src
proa site check
```

When publishing a route manifest, capture the route report as an artifact:

```bash
proa site routes --json > proa-routes.json
```

## What It Does Not Prove

`proa site` catches structural drift in the generated site convention. It does not replace:

- `cargo check` for Rust type errors.
- `cargo test` for route behavior.
- `proa fmt --check --verify` for template parse stability.
- `proa lint` for accessibility, composition, and render-path diagnostics.
- A live HTTP smoke test for deployed Axum routes.
