Routing is explicit Rust. A URL exists once `src/routes.rs` registers it. Files under `src/pages/` hold handlers and Page components by convention; a file's name or location never creates a route.

```rust filename="src/routes.rs"
use axum::routing::get;
use proa::axum::{router_from_spec, Route};

let (router, metadata) = router_from_spec(vec![
    // proa:route-specs:start
    Route::endpoint("/", get(pages::home::handler)),
    Route::endpoint("/issues/{id}", get(pages::issue::handler)),
    // proa:route-specs:end
]);
```

A site from `proa new site` registers its pages in this block; the starter ships the `/` line. `Route::endpoint(path, handler)` pairs a URL pattern with an Axum method router, and `router_from_spec` turns the list into an ordinary Axum `Router` plus the route metadata that `FrameworkBuilder::with_dynamic_routes_and_metadata` takes. Nothing scans `src/pages/`.

The two `proa:route-specs` lines are ordinary comments. `proa generate page` and `proa generate endpoint` insert their `Route::endpoint(...)` line directly above the `:end` comment, and that is their only job: the compiler and the running server ignore them. Add, reorder, and remove the lines between them by hand. If the `:end` comment is missing, the generators stop with `generated ownership marker ... is missing` and change nothing. The `proa:explicit-routes` pair lower in the same file marks where `proa generate page` adds the `.route("/about.md", ...)` line for an explicit Markdown URL.

## Give a new page a URL

The generator does every step:

```bash
proa generate page about
```

By hand, a new file under `src/pages/` needs three edits, and a fourth for a Markdown URL:

1. Declare the module in `src/pages/mod.rs`: `pub mod about;`.
2. Write the Page component and its `handler` function in `src/pages/about.rs`. The Page declares `const ROLE: ComponentRole = ComponentRole::PAGE`.
3. Register the route in `src/routes.rs`, between the `proa:route-specs` comments: `Route::endpoint("/about", get(pages::about::handler)),`.
4. Optional: register the explicit Markdown URL between the `proa:explicit-routes` comments: `.route("/about.md", get(pages::about::markdown))`.

[Add A Route](/docs#5-add-a-route) in the Quickstart has the complete code for steps 1 to 3, and [Content negotiation](/docs/framework/content-negotiation) covers the Markdown handler. Run `proa site routes` to list every route the site registers. See [proa generate](/docs/cli/generators#pages) for the generator's flags.

## Path syntax

Paths use Axum 0.8 syntax: `{id}` captures one segment and `{*rest}` captures the rest of the path. The colon form from Axum 0.7 no longer captures:

| You write | What happens |
| --- | --- |
| `.route("/issues/{id}", get(issue))` | Captures `id`. |
| `.route("/issues/:id", get(issue))` | Panics while the router is built, before the server accepts a request: ``Path segments must not start with `:`. For capture groups, use `{capture}`.`` |
| `Route::endpoint("/issues/:id", get(issue))` | Registered as `/issues/{id}`. Route specifications still accept `:id` and `*rest` written for earlier versions; write braces in new code. |

## Register a route

`router_from_spec` builds on plain Axum, and a plain Axum `Router` works too. This route sends `/shop/products/42` to the `product` handler:

```rust filename="Routes"
use axum::{routing::get, Router};

let routes = Router::new()
    .route("/shop/products/{id}", get(product));
```

The handler composes the document, shared shop layout, and selected Page:

```rust filename="Product handler"
use proa::axum::RouteResponse;
use crate::{layouts::{RootDocument, ShopLayout}, pages::ProductPage};

async fn product() -> RouteResponse {
    RouteResponse::ssr(RootDocument {
        children: ShopLayout {
            children: ProductPage,
        },
    })
}
```

![The file tree and explicitly composed layouts lead to one selected Page.](/static/images/docs/nested-layouts.svg)

`RootDocument` and `ShopLayout` declare `const ROLE: ComponentRole = ComponentRole::LAYOUT`; `ProductPage` declares `PAGE`. See [Layouts and Pages](/docs/framework/layouts-and-pages) for their full implementations and document markup.

### Install the router

Pass the router to `FrameworkBuilder`. Enable managed metadata with `with_head`:

```rust filename="App configuration"
use proa::{HeadConfig, HeadUrlPolicy};
use proa::axum::FrameworkBuilder;

let head = HeadConfig::default()
    .with_urls(HeadUrlPolicy::new("https://acme.example", "/")?);

let app = FrameworkBuilder::new()
    .with_head(head)
    .with_dynamic_routes(routes)
    .try_build()?;
```

Use your configured public origin in place of `https://acme.example`. The framework makes Axum's matched path parameters available through `cx` before head and body rendering.

## Read route parameters from cx

A `{name}` segment captures a path value, and `{*name}` captures the rest of the path:

| Route | Request | Read through cx |
| --- | --- | --- |
| `/shop/products/{id}` | `/shop/products/42` | `cx.param("id")` → `Some("42")` |
| `/blog/{slug}` | `/blog/red-shoes` | `cx.param("slug")` → `Some("red-shoes")` |

These are URL patterns, registered explicitly; Rust filenames organize the source code.

Here is the `ProductPage` used above. It reads the same `id` in its head and body:

```rust check="product" filename="src/pages/product.rs"
use proa::{
    ComponentRole, DataLoader, SyncHeadOperation, WebContext, WebRenderSync,
    WriteError,
};
use proa::html_sync;

pub struct ProductPage;

impl<L: DataLoader> WebRenderSync<L> for ProductPage {
    const ROLE: ComponentRole = ComponentRole::PAGE;

    fn render_head(&self, cx: &mut WebContext<L>) -> impl SyncHeadOperation {
        let id = cx.param("id")
            .ok_or_else(|| WriteError::render("missing product id"))?;
        let title = format!("Product {id}");
        cx.head_mut().title(title)
    }

    fn render(self, cx: &mut WebContext<L>) -> Result<(), WriteError> {
        let params = cx.route_params().cloned().unwrap_or_default();
        let id = params.get("id")
            .ok_or_else(|| WriteError::render("missing product id"))?;

        html_sync! {
            <main data-product-page>
                <h1>"Product "{id}</h1>
            </main>
        }
        .render(cx)
    }
}
```

`cx.param(name)` returns `Option<&str>`. `cx.route_params()` exposes the shared collection. Clone that handle before rendering when the template needs to borrow a parameter while writing through `cx`; this does not copy parameter strings.

For `/shop/products/42`, `ShopLayout`'s `title_template("%s | Shop")` formats the Page's dynamic title:

```html filename="Selected output"
<title>Product 42 | Shop</title>
<main data-product-page><h1>Product 42</h1></main>
```

The title goes in the document head and `<main>` in its body. Title templates work the same for `{id}` and `{slug}`: the Page supplies its title, often from a loader, and the nearest ancestor template formats it. A slug is not automatically turned into a display title. See [Load metadata from data](/docs/framework/metadata#load-metadata-from-data) for an async example.

### Query strings

Path captures and query strings are separate:

```rust filename="Inside a render method or head hook"
let path = cx.request_location().map(|location| location.path());
let query = cx.request_location().and_then(|location| location.query());
```

For `/shop/products/42?currency=usd`, these return `Some("/shop/products/42")` and `Some("currency=usd")`. `query()` returns the raw query string. Use a query parser or Axum's typed `Query` extractor for decoded fields.

## Add and nest routes

Chain `.route(...)` calls to add Pages. Use Axum's `.nest(...)` to share a URL prefix:

```rust filename="More routes"
let shop = Router::new()
    .route("/", get(shop_index))
    .route("/products/{id}", get(product));

let routes = Router::new()
    .route("/about", get(about))
    .nest("/shop", shop);
```

This registers `/about`, `/shop`, and `/shop/products/{id}`; Axum maps the nested `/` route to the prefix itself. Each handler explicitly composes its layout and Page. URL nesting does not add HTML wrappers.

### Route specifications

`Route::endpoint` is the form the starter uses, shown at the top of this page. Use it when you also need route modes, static-path declarations, page-cache policy, or route-specification metadata. A single specification also produces an Axum router you can merge with the rest of the app:

```rust filename="Route specification"
use proa::axum::{Route, RouteMode};

let routes = Router::new().merge(
    Route::endpoint("/shop/products/{id}", get(product))
        .with_route_mode(RouteMode::Server)
        .into_router(),
);
```

`Server`, `Static`, and `ClientBrowser` describe routes to tooling; they do not set component roles or compose layouts. The older `Route::layout` and `Route::page` APIs describe route metadata independently of `render_head`. See [metadata migration](/docs/framework/metadata#existing-metadata-code) when updating those documents.
