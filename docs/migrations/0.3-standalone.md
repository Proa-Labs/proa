# Migrating to Proa 0.3

Proa 0.3 establishes this repository as the complete source boundary for the
compiled-template framework. The coordinated `proa_core`, `proa_macros`,
`proa_stream`, `proa_react`, `proa_actions`, `proa_framework_core`, and
`proa_framework_axum` release group moves to `0.3.0`.

Several independently versioned crates also cross breaking-release boundaries:
`proa_codegen`, `proa_docs`, and `proa_docs_build` move to `0.2.0`. The
coordinated `rsjs`, `rsjs_ir`, and `rsjs_macros` group moves to `0.2.0`. The
shared `proa_ir` and `proa_dsl` baselines move to `0.1.2` and `0.1.3`,
respectively, so packaged builds cannot resolve registry copies from before
the standalone boundary.

Support crates whose earlier registry artifacts predate the public license
boundary receive fresh `0.1.2` versions: `proa_const_json`, `proa_const_json_macros`,
`itoa_lut`, `proa_og`, `proa_tailwind_merge`, and `proa_tailwind_merge_macro`. Registry
versions are immutable, so these new versions are required even where the Rust
API did not otherwise need a breaking change.

Update direct dependencies together:

```toml
[dependencies]
proa_core = "0.3.0"
proa_macros = "0.3.0"
proa_framework_axum = "0.3.0"
proa_docs = "0.2.0"
rsjs = "0.2.0"
```

Proa libraries resolve from crates.io. Commit Cargo.lock; repository-local
`path` entries remain available for workspace development. No private Cargo
index or token is required. The JSON and Tailwind helper packages retain their
original Rust crate names; see [Package distribution](../registry.md).

## Standard render buffer

Use `proa_core::RenderBuffer` for ordinary buffered rendering:

```rust
use proa_core::RenderBuffer;

let mut output = RenderBuffer::new();
```

`DefaultChainedBumpWriter` remains available as a deprecated compatibility
alias. Code that deliberately tunes the page size should continue to use
`ChainedBumpWriter<N>`.

## Component-tree ownership

`html_tree!` and `html_with_tree!` now emit the product-neutral component-tree
types owned by `proa_ir`, rather than types from a downstream component
library. Applications that use either macro must add the new IR baseline:

```toml
proa_ir = "0.1.2"
```

Import explicit tree types from `proa_ir::component_tree`. Applications that
only use the HTML or Markdown render macros do not need a direct `proa_ir`
dependency.

## Removed native-mobile surface

The incomplete native-mobile target was coupled to a downstream component
library and is not part of the standalone compiled-template framework. The
following exports were removed:

- `proa_core::mobile`, `MobileContext`, and `MobileRender`;
- `proa_macros::mobile_const!`; and
- the `Section` and `Screen` derives.

Applications that need server-driven native UI should keep their native schema,
component catalog, encoding, and derives in the integration crate that owns
those client contracts. The supported Proa targets in this repository are web,
email, and Markdown rendering.

## Removed runtime-template and legacy `Vm*` surface

Runtime templates are source supplied as data and validated after the host
application has been built. They are a downstream integration rather than a
prerequisite of the compiled-template crates. The `VmComponent`, `VmPropEnum`,
and `VmScopeRoot` derives were therefore removed from `proa_macros`, along with
the runtime-template implementation workspace.

Compiled Rust templates should continue to use `html_sync!`, `html!`,
`md_sync!`, and `md!`. A runtime-template product should own its compiler,
component catalog, validation policy, interpreter, and any derives that bind
compiled components into that catalog.

## Removed documentation-build adapters

`proa_docs_build` remains a standalone build-time Markdown/MDX compiler. Its
runtime-document adapter was removed, including:

- `DocumentVmBuildConfig`, `DocumentVmBuildConfigError`, and
  `NormalizedRelativePath`;
- `DocsSource::document_vm` and `DocsSource::document_vm_config`;
- the `*_with_document_components` compile and link-validation functions; and
- runtime-document-specific `CompileError` variants.

Use `compile`, `compile_docs`, `try_compile`, `try_compile_to`, and
`validate_links` for repository-owned documentation. Runtime-document products
should provide their adapter in the repository that owns the runtime compiler
and component catalog.

## Removed product-specific route code generation

`proa_codegen` now generates React component sources from product-neutral JSON
metadata. It no longer exports `RouteGenerator`, `RouteManifest`, or
`RouteMode`, and its binary no longer invokes a particular example application
or writes into a neighboring frontend tree.

The framework's `route-export` feature and
`proa_framework_axum::route_export` module remain available for serializing route
metadata. Consumers that need TypeScript routes should translate that exported
metadata in their own frontend build, where router package names and output
paths are known.
