title: Images
description: Serve responsive images from static assets, without a build pipeline.

Proa has no image optimization pipeline. It renders the `<img>` tag you write, with typed attribute support for `srcset`, `sizes`, `imagesrcset`, and `imagesizes`, and serves the files from your static directory.

```rust filename="src/components/hero.rs"
html_sync! {
    <img
        src="/static/images/hero-800.avif"
        srcset="/static/images/hero-400.avif 400w,
                /static/images/hero-800.avif 800w,
                /static/images/hero-1600.avif 1600w"
        sizes="(max-width: 640px) 100vw, 800px"
        width="800"
        height="450"
        alt="Coastal cliffs at sunrise"
        fetchpriority="high"
        decoding="async"
    />
}
```

That is the whole API. What follows is how to make it fast.

## The four attributes that matter

| Attribute | Why |
|---|---|
| `width` and `height` | Reserve the box before the bytes arrive. Without them the page reflows and your CLS score suffers |
| `loading="lazy"` | Defer offscreen images. Never put it on your largest above-the-fold image |
| `decoding="async"` | Keep decode work off the critical path |
| `srcset` + `sizes` | Let the browser pick a file matching the device, instead of shipping a desktop image to a phone |

`srcset` without `sizes` is a common mistake: the browser assumes the image is viewport-width and often picks a file larger than it needs.

> **Good to know**: For the one image that is your Largest Contentful Paint, add `fetchpriority="high"` and leave `loading` off entirely. Lazy-loading your hero image is a measurable regression.

## Generating the variants

Resizing is a build step you own. Generate the sizes ahead of time and commit them, or produce them in CI before `proa build`:

```bash
for w in 400 800 1600; do
  magick hero.jpg -resize ${w}x -quality 82 public/images/hero-${w}.avif
done
```

Prefer AVIF, then WebP, then JPEG. If you need per-format fallbacks rather than per-width, use `<picture>`:

```rust filename="src/components/hero.rs"
html_sync! {
    <picture>
        <source srcset="/static/images/hero.avif" type="image/avif" />
        <source srcset="/static/images/hero.webp" type="image/webp" />
        <img src="/static/images/hero.jpg" width="800" height="450" alt="Coastal cliffs" />
    </picture>
}
```

## Hosting responsive variants outside the application

For bundled images, export the immutable files alongside the release and configure `PROA_ASSET_PREFIX` to point at the bucket or CDN that serves them. Upload the entire immutable tree before switching HTML traffic, and retain earlier hashes while old pages can still reference them. [Static assets](/docs/framework/static-assets)

For user uploads, keep object identifiers in your database and generate delivery URLs from a server-owned host and approved variant sizes. Create 400, 800, and 1600 pixel variants on upload in S3 or R2, or request those widths through a service such as Cloudflare Images. Render the corresponding absolute HTTPS URLs in `srcset`, provide the intrinsic width and height, and set `sizes` to the actual layout width. For private media, issue short-lived signed delivery URLs only after checking access. [Cloudflare image transformations](https://developers.cloudflare.com/images/transform-images/transform-via-url/)

## Serving them

Images live under the directory your static service points at, `public/` in scaffolded sites. See [Static assets](/docs/framework/static-assets) for mounting and cache headers.

Give generated filenames a content hash and a long `max-age`. Stable names such as `hero.avif` need a revalidation policy or a versioned URL so updates reach browsers.

In MDX content, `MdxImageConfig` rewrites authored paths at build time, so `/images/hero.avif` in a Markdown file can resolve to `/static/images/hero.avif` in the output:

```rust filename="build.rs"
.images(MdxImageConfig::new().rewrite_prefix("/images/", "/static/images/"))
```

## Open Graph images

Social preview images can be shared static files or generated per page. The optional `proa_og` crate can render images with WPE WebKit on Linux and requires its native libraries; it is separate from the metadata API. Metadata points to an existing image URL and does not invoke a renderer. See [Metadata and OG images](/docs/framework/metadata).
