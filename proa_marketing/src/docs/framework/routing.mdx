Proa route declarations are regular Rust values. You define a route tree with `Route`, then turn it into an Axum `Router` with `router_from_spec`.

## Route Tree

```rust
use axum::routing::get;
use proa_framework_axum::{router_from_spec, Route, RouteMode};

let (routes, setups) = router_from_spec(vec![
    Route::layout(
        "",
        &AppLayout,
        vec![
            Route::page("/", "Home", get(home)).with_route_mode(RouteMode::Server),
            Route::page("/about", "About", get(about)).with_route_mode(RouteMode::Static),
            Route::page("/dashboard", "Dashboard", get(dashboard))
                .with_route_mode(RouteMode::ClientBrowser),
        ],
    ),
]);
```

The generated router contains the Axum routes. The second value contains ordered route setup plans; pass it to `FrameworkBuilder::with_dynamic_routes_and_setups`. Layout callbacks run with each real request before the page. Registration does not compute final metadata.

For JSON APIs, form submissions, webhooks, health checks, and other non-page routes, use [Route handlers](/docs/framework/route-handlers).

## Route Constructors

| Constructor | Use it for |
|-------------|------------|
| `Route::endpoint(path, router)` | Raw endpoint without generated title metadata. |
| `Route::page(path, title, router)` | Page endpoint with title-only metadata. |
| `Route::layout(path, layout, children)` | Metadata layout shared by child routes. |

## Route Modes

`RouteMode` describes how a route should be treated by build and client-routing tooling.

| Mode | Use it when |
|------|-------------|
| `Server` | The route is rendered by the server at request time. |
| `Static` | The route can be pre-rendered by build tooling. |
| `ClientBrowser` | The route participates in client-side browser navigation. |

The mode does not replace your Axum handler. It is metadata for Proa's route tooling and export pipeline.

## Dynamic Static Paths

Static dynamic routes can provide path parameters:

```rust
use std::collections::HashMap;

use axum::routing::get;
use proa_framework_axum::{Route, RouteMode};

fn blog_paths() -> Vec<HashMap<&'static str, String>> {
    vec![
        HashMap::from([("slug", "intro".to_string())]),
        HashMap::from([("slug", "routing".to_string())]),
    ]
}

let route = Route::<()>::page("/blog/:slug", "Blog Post", get(blog_handler))
    .with_route_mode(RouteMode::Static)
    .with_static_paths(blog_paths);
```

The keys match the `:param` names in the route path.

## Layouts

A registered route layout supplies request-time defaults through the live `WebContext`. Matched layouts run outermost to innermost in separate route scopes, followed by the page scope:

```rust
use proa_core::{DynLoaderHandle, WebContext, WriteError};
use proa_framework_axum::{Layout, Metadata};

pub struct AppLayout;

impl Layout for AppLayout {
    fn setup(&self, cx: &mut WebContext<DynLoaderHandle>) -> Result<(), WriteError> {
        cx.metadata(Metadata::new().title("Acme").title_template("%s · Acme"));
        Ok(())
    }
}
```

Implement `setup_send` with `SendWebContext<DynLoaderHandle>` too when serving compiler-proved Send responses. The default reports an unsupported layout instead of silently omitting defaults. Await page data in the page's normal render path, then declare metadata before emitting `{cx.metadata.head()}`. See [Metadata and OG images](/docs/framework/metadata) for the full flow.

Compose shared HTML chrome explicitly in the render tree, normally with a reusable `RootDocument` component:

```rust
use proa_framework_axum::RouteResponse;

// Load page data and declare its metadata before invoking RootDocument.
RouteResponse::ssr(ProductPage)
```

Ordinary document wrappers share the current scope; they do not become registered layouts by name or nesting. They must emit the head after metadata-dependent page preparation. The same declaration deadline applies to synchronous, buffered async, and streaming routes.
