# Proa releases

Use `scripts/release-plz.sh` and the **Release crates** Actions workflow as the
single release path. Read [the release guide](../../../scripts/README.md#cratesio-releases)
for tool installation, credentials, recovery, and workflow inputs. Run commands
from the repository root; use authenticated `gh` for GitHub operations.

## Prepare versions

1. Start from a clean checkout of current `main`. Install the pinned tools with
   `scripts/release-plz.sh install`, then run `scripts/release-plz.sh check`.
2. Run `scripts/release-plz.sh release-pr`, or dispatch the same operation:

   ```sh
   gh workflow run release-plz.yml --ref main -f command=release-pr
   ```

3. Review the generated package versions, dependency requirements, lockfile, and
   changelogs. Release-plz owns these changes: do not hand-bump manifests or
   invent scaffold versions. If an explicit version override is needed, use the
   wrapper's `set-version` operation, then regenerate and validate the release PR.
4. Get the release PR through CI and the repository's merge process before
   publishing. Preparing a release does not authorize a merge or an upload.

## Include the CLI and generated projects

`proa_cli/Cargo.toml` declares scaffold libraries as dev-dependencies.
Release-plz updates those requirements and bumps the CLI when a scaffold library
changes. `proa_cli/build.rs` derives the embedded scaffold catalog from those
Cargo declarations, resolving workspace inheritance during local builds and
Cargo's normalized manifest during packaged builds. Templates consume that
catalog; there must be no separately maintained version list or manual template
pin update.

The shared `check` preflight runs `scripts/check_release_scaffold.py` with the
pinned release-plz. It changes only a library in temporary fixtures and checks
that both patch and minor releases bump the CLI, update its requirement, and
reach the catalog produced by the real CLI build script. When changing scaffold
libraries or manifests, also run the existing scaffold tests.

## Publish and verify

After the release PR is merged, use current `main` and run
`scripts/release-plz.sh release-dry-run`. With explicit publication authorization,
run `scripts/release-plz.sh release` (or select the same Actions operation).
Do not replace this with individual `cargo publish`, manual tags, or a separate
CLI release sequence.

The wrapper publishes libraries first, builds the candidate CLI, and runs
`scripts/check_registry_install.py` for all five `proa new site` templates with a
fresh Cargo home. Only successful crates.io resolution, builds, tests, and HTTP
checks allow CLI publication. Its tag triggers **Release CLI** binary packaging.
A passing preflight or local workspace build is not evidence that new versions
are published. Report registry failures accurately; do not work around them by
putting Git URLs or workspace paths into generated projects.
