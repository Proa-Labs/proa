title: Content negotiation
description: Serve HTML and Markdown representations of one resource through HTTP content negotiation.

One URL can serve HTML to a browser and Markdown to an agent. Give a page an HTML and a Markdown implementation, then let `negotiate` choose from the request's `Accept` header:

```rust filename="src/pages/guide.rs"
use axum::http::{HeaderMap, StatusCode};
use axum::response::IntoResponse;
use proa::axum::{explicit_markdown, negotiate, MarkdownAlternate, RouteResponse};
use proa::{html_sync, md_sync, DataLoader, MdRenderSync, WebContext, WebRenderSync, WriteError};

#[derive(Clone, Copy)]
pub struct GuidePage {
    pub title: &'static str,
    pub body: &'static str,
}

impl<L: DataLoader> WebRenderSync<L> for GuidePage {
    fn render(self, cx: &mut WebContext<L>) -> Result<(), WriteError> {
        html_sync! {
            <main>
                <h1>{self.title}</h1>
                <p>{self.body}</p>
            </main>
        }
        .render(cx)
    }
}

impl<L: DataLoader> MdRenderSync<L> for GuidePage {
    fn render_md(self, cx: &mut WebContext<L>) -> Result<(), WriteError> {
        md_sync! { r#"
            # {self.title}

            {self.body}
            "#
        }
        .render_md(cx)
    }
}

const GUIDE: GuidePage = GuidePage {
    title: "Install",
    body: "Install the CLI with Cargo",
};

/// `GET /guide`: HTML by default, Markdown when the client prefers it.
pub async fn guide(headers: HeaderMap) -> Result<impl IntoResponse, StatusCode> {
    negotiate(&headers, RouteResponse::ssr(GUIDE), GUIDE, MarkdownAlternate::new("/guide.md"))
        .map_err(|_| StatusCode::INTERNAL_SERVER_ERROR)
}

/// `GET /guide.md`: always Markdown.
pub async fn guide_markdown() -> Result<impl IntoResponse, StatusCode> {
    explicit_markdown(GUIDE).map_err(|_| StatusCode::INTERNAL_SERVER_ERROR)
}
```

Register both routes and mount them through `FrameworkBuilder`, which installs the route context `RouteResponse` renders in. On a bare `Router`, the HTML response is a 500:

```rust filename="src/routes.rs"
use axum::{routing::get, Router};
use proa::axum::FrameworkBuilder;
use crate::pages::guide::{guide, guide_markdown};

pub fn router() -> Result<Router, Box<dyn std::error::Error>> {
    let routes = Router::new()
        .route("/guide", get(guide))
        .route("/guide.md", get(guide_markdown));
    Ok(FrameworkBuilder::new().with_dynamic_routes(routes).try_build()?)
}
```

The HTML response advertises the Markdown URL:

```http
GET /guide

HTTP/1.1 200 OK
content-type: text/html; charset=utf-8
vary: Accept
link: </guide.md>; rel="alternate"; type="text/markdown"
```

The same URL returns Markdown when the client asks for it:

```http
GET /guide
Accept: text/markdown

HTTP/1.1 200 OK
content-type: text/markdown; charset=utf-8
vary: Accept
```

Sites generated with Markdown representations use these functions in their page handlers. Add them to an existing site with `proa add representation markdown`; `proa generate page` then writes both handlers.

## Dynamic routes

`MarkdownAlternate::new` takes a route pattern, not a finished URL. Write the route's captures into it and Proa fills them in from the current request:

```rust filename="src/pages/issue.rs"
use axum::extract::Path;
use axum::http::{HeaderMap, StatusCode};
use axum::response::IntoResponse;
use proa::axum::{explicit_markdown, negotiate, MarkdownAlternate, RouteResponse};

const ISSUE_MARKDOWN: MarkdownAlternate = MarkdownAlternate::new("/issues/{id}/index.md");

/// `GET /issues/{id}`: HTML, or Markdown when the client prefers it.
pub async fn issue(
    Path(id): Path<u32>,
    headers: HeaderMap,
) -> Result<impl IntoResponse, StatusCode> {
    let page = IssuePage { id };
    negotiate(&headers, RouteResponse::ssr(page), page, ISSUE_MARKDOWN)
        .map_err(|_| StatusCode::INTERNAL_SERVER_ERROR)
}

/// `GET /issues/{id}/index.md`: always Markdown.
pub async fn issue_markdown(Path(id): Path<u32>) -> Result<impl IntoResponse, StatusCode> {
    explicit_markdown(IssuePage { id }).map_err(|_| StatusCode::INTERNAL_SERVER_ERROR)
}
```

`IssuePage` is a `Copy` struct with an `id: u32` field and the same two render implementations as `GuidePage`. Register both patterns:

```rust filename="src/routes.rs"
let routes = Router::new()
    .route("/issues/{id}", get(issue))
    .route("/issues/{id}/index.md", get(issue_markdown));
```

A request for `/issues/42` advertises the concrete URL:

```http
GET /issues/42

HTTP/1.1 200 OK
content-type: text/html; charset=utf-8
vary: Accept
link: </issues/42/index.md>; rel="alternate"; type="text/markdown"
```

The path is a `&'static str` because it is the pattern. When the `Link` header is written, each `{name}` in it is replaced with the request's route parameter of that name, percent-encoded as one path segment, so the handler builds no URL string. A `{name}` the route does not capture is left as written. Under a [URL path prefix](/docs/framework/deployment#serving-behind-a-url-path-prefix) the prefix is added: the same handler mounted at `/tracker` advertises `</tracker/issues/42/index.md>`.

`proa generate page issues/{id}` writes the suffix form, `MarkdownAlternate::new("/issues/{id}.md")`. Axum matches a whole path segment, so one route serves both `/issues/42` and `/issues/42.md`: the generated `handler_with_markdown_alias` checks the request path for the `.md` suffix, and `MARKDOWN_ALTERNATE.render_explicit(page)` removes the suffix from the capture before the Markdown renders.

## Pages that load data

When the Markdown representation awaits loader data, the page implements `MdRender<L>` and the handler passes one request-scoped resolver to both representations. This is the home page handler `proa new site` writes for a site with a database:

```rust filename="src/pages/home.rs"
use axum::{extract::State, http::HeaderMap, response::IntoResponse};
use proa::axum::{
    explicit_markdown_async_with_loader, negotiate_async_with_loader, MarkdownAlternate,
    RouteResponse,
};
use proa::stream::DataResolver;

use crate::{app::AppState, error::AppError, layouts::RootDocument};

pub async fn handler(
    State(state): State<AppState>,
    headers: HeaderMap,
) -> Result<impl IntoResponse, AppError> {
    let resolver = DataResolver::request_scope(state.loader.clone());
    let html =
        RouteResponse::ssr_async_with_loader(RootDocument { content: HomePage }, resolver.clone());
    Ok(negotiate_async_with_loader(
        &headers,
        html,
        HomePage,
        resolver,
        MarkdownAlternate::new("/index.md"),
    ))
}

pub async fn markdown(State(state): State<AppState>) -> Result<impl IntoResponse, AppError> {
    let resolver = DataResolver::request_scope(state.loader.clone());
    Ok(explicit_markdown_async_with_loader(HomePage, resolver))
}
```

`negotiate_async_with_loader` returns a response plan rather than a `Result`: it picks the representation from the headers, and the selected renderer runs when the response is finalized. See [Data loading and streaming](/docs/framework/data-loading) for the loader and resolver.

## The API

All of these live in `proa::axum`:

| Item | Use |
|---|---|
| `negotiate(&headers, html, markdown, alternate)` | Canonical URL. Returns the HTML response with a `Link: rel="alternate"` header, or the Markdown body when the client prefers it. Both add `Vary: Accept`. |
| `explicit_markdown(markdown)` | Stable `.md` URL. Always Markdown, with no negotiation and no `Vary`. |
| `MarkdownAlternate::new(path)` | The advertised Markdown path. A `{name}` capture such as `/guides/{slug}.md` expands to the current route parameter, percent-encoded. See [Dynamic routes](#dynamic-routes). |
| `MarkdownAlternate::render_explicit(markdown)` | Serves a captured alias such as `/guides/{slug}.md` with `.md` removed from the final capture, so the renderer sees the same `slug` as the HTML page. |
| `negotiate_async_with_loader` / `explicit_markdown_async_with_loader` | The same two responses for an `MdRender<L>` that awaits loader data. The handler stays `Send`; rendering runs when the response is finalized. See [Pages that load data](#pages-that-load-data). |

The Markdown representation renders without the HTML document shell. See [Markdown rendering](/docs/core/markdown) for `MdRenderSync`, `MdRender`, and `md_sync!`.

## How the representation is chosen

Markdown wins only when the client gives `text/markdown` a positive quality greater than the quality that applies to HTML. Everything else stays on HTML:

| `Accept` | Response |
|---|---|
| `text/markdown` | Markdown |
| `text/html;q=0.4, text/markdown;q=0.9` | Markdown |
| `text/html, text/markdown` | HTML (equal preference) |
| `text/markdown;q=0.5, */*;q=1` | HTML (the wildcard covers HTML at a higher quality) |
| `text/markdown;q=0, text/html;q=0.1` | HTML |
| `*/*`, `text/*`, or no header | HTML |

## Why not a separate agent endpoint

The alternative is a parallel surface: a site, an API, an `llms.txt`, a scraping adapter, and an agent-specific endpoint for every piece of public information. Each one is a thing to build, secure, and keep in sync.

Multiple representations of one resource is the design the web already has. `rel="alternate"` is [RFC 8288](https://www.rfc-editor.org/rfc/rfc8288) web linking, and content negotiation is as old as HTTP. The agent needs no prior knowledge of your conventions beyond the standard.

## Two layers, not one

`.well-known` and `rel="alternate"` answer different questions, and an agent needs both:

| Question | Mechanism |
|---|---|
| What can I *read* here? | `Link: rel="alternate"` on the resource |
| What can I *do* here? | `rel="service-desc"`, OpenAPI, MCP |

Reading is a representation problem. Acting is a service-description problem. Do not collapse them into one endpoint.

## Caching, before you ship it

An HTTP cache that honors `Vary: Accept` keeps representations separate. Raw `Accept` values can create many variants because clients send different preference lists. Cloudflare does not honor arbitrary `Vary` fields by default; enable its [Vary support](https://developers.cloudflare.com/cache/concepts/vary/) or explicitly include the selected representation in the cache key before caching negotiated routes.

Choose a representation policy:

- **Normalize `Accept` at the edge** to the representations you actually serve, preserving the origin's negotiation semantics, and include that choice in the cache key. Changing the forwarded header alone does not separate cached responses.
- **Use the `.md` URL for Markdown caching** and bypass shared caching on the negotiated canonical URL until its variants are configured. A separate Markdown URL does not by itself make a URL-only cache safe for the canonical route.

See [Page caching](/docs/framework/page-caching).

> **Good to know**: Markdown is a good representation for today's models, not the final destination. The same `Link` mechanism carries `application/ld+json` for entity data or an OpenAPI document for actions. The page advertises its interfaces; the agent picks the one that fits the job.
